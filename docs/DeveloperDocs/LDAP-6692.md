## September 23 recurrence (Snap 11.90)

Read the full issue and all six comments again. The reporter confirms the earlier
bind/search fix worked, then reports a new failure after successful LDAP
authentication, local-user lookup and fullname synchronization. This differs
from the September 14 optional-filter exception.

The current browser form reproduced two requests for one click: password login
ran while the click handler awaited authentication-method lookup, then LDAP ran.
The LDAP callback discarded its error and redirected to `/` unconditionally.
The loading flag also destroyed and recreated the form. The result was a silent
return to sign-in. The logged `user.email` value is not evidence of missing
addresses: stored Meteor accounts use `user.emails`.

Capture the form's submit event before useraccounts handles it, synchronously
cancel it while selecting the provider, and preserve the mounted form. Both
Enter and button clicks now use one login path; duplicate pending submissions
are ignored. Delegate password submissions back to the original form handler
for validation and 2FA. Provider errors remain visible as text; successful
completion uses the normal AccountsTemplates callback and session-aware redirect.
Remove the capture listener when the layout is destroyed.

Seven focused tests cover ordering, pending duplicates, rejection/retry, lookup
and provider exceptions, password replay, empty inputs, unrelated forms and
CAS/SAML completion. Existing LDAP filter, email mapping, connection-release and
password-guard suites pass. A fresh production Meteor build and four Chromium
regressions passed with an isolated FerretDB SQLite backend. Browser checks cover
click/Enter failures, retained fields and retry, actual DDP session completion
using a fixture resume token, and the original password path. The directory
callback is controlled in these UI tests; no live external LDAPS bind or Snap
installation was tested. FerretDB's current resume-token query/projection code
was reviewed; this reproduced defect requires no database changes.

## September 24: invitation rejection disabled the account

The reporter's [follow-up](https://github.com/wekan/wekan/issues/6692#issuecomment-5811473169)
confirms that LDAP authentication succeeded. Accepting an invitation in the board
sidebar with an existing session called `removeInvite`, a direct client write to
`profile.invitedBoards`. The security guard correctly refused that protected
write, but logged it as InviteProfileBleed and disabled the account.

The sidebar now calls the existing server `acceptInvite` method, which checks the
pending invitation before consuming it. Decline relies on `quitBoard` to remove
the invitation; it no longer sends a second client write. Both methods explicitly
require a logged-in caller. Forged invitation writes remain forbidden.

The signed-out sign-in form now uses the configured authentication provider
without subscribing to protected user metadata. That unnecessary subscription
caused the repeated anonymous MembershipBleed entries shown in the screenshot.
The publication's authentication guard remains active.

An administrator must re-enable an already affected account in Admin Panel /
People after reviewing its recorded block reason. Existing blocks are not cleared
automatically: the historical log cannot distinguish a legitimate sidebar action
from a forged write. No LDAP settings or TLS checks need changing for this case.

The other screenshot entries are separate: filename shortening and a clean
storage scan are informational events, not account blocks. The HistoryIntegrity
checksum mismatch cannot be diagnosed from a hash alone. It needs the affected
stored history row and its predecessor, with content preserved for local hash
comparison; do not clear or regenerate the hashes merely to suppress the report.
The background audit records a detection and does not disable accounts.

Focused handler and method tests pass. Browser acceptance/decline regressions are
registered in `72-invitation-profile.e2e.js` and syntax-checked; they still need a
running Meteor/database/browser stack. No external LDAP or deployed Snap was
available for this follow-up.

Tổng quan kiến trúc

Hệ thống được chia thành ba lớp: lớp quy ước vận hành, lớp quản lý trạng thái, và lớp xử lý phản hồi. Cách tách này giúp dự án có kỷ luật, dễ mở rộng và dễ bàn giao.

PM Người đứng đầu dự án, chốt ưu tiên, chia task và tổng hợp trạng thái.
Developer / Agent Thực thi thay đổi đúng phạm vi, ghi chú rõ và không phá cấu trúc cũ.
Customer Reviewer Đánh giá giao diện và chức năng theo góc nhìn người dùng thật.

Flow và Pipeline

Luồng vận hành đi từ nhận yêu cầu đến bàn giao cuối cùng, với từng bước có file lưu trạng thái riêng để không bị đứt mạch.

Bước Mục đích Đầu vào Đầu ra
Intake Chuẩn hóa yêu cầu Mô tả task requirements.md
Plan Chia việc và xác định hướng xử lý Yêu cầu + ràng buộc current_task.md
Implement Sửa đúng phần cần sửa Kế hoạch + code Diff, notes
QA Xác nhận kết quả Build / thay đổi mới test-report.md
Feedback Xử lý phản hồi Feedback mới responses.md, action-plan.md
Handoff Bàn giao và tổng kết Tất cả state final_report.md

Chi tiết từng chức năng

.agent

Chứa skills, rules, workflows và roles. Đây là phần mô tả “cách làm việc” của hệ thống. Nó trả lời câu hỏi: ai làm, làm theo luật nào, và đi qua những bước nào.

.manager

Chứa state file cho PM và các vai trò khác. Đây là sổ cái vận hành, giúp nhìn nhanh task đang ở đâu, đã kiểm thử chưa, và còn gì cần chốt.

.feedback

Chứa luồng inbox -> response -> action plan. Đây là nơi gom phản hồi rời rạc thành việc có thể xử lý và theo dõi đến khi đóng xong.

refer/

Chứa tài liệu phân tích chi tiết, giúp người mới đọc vào là hiểu cấu trúc, luồng xử lý và các đề xuất mở rộng của dự án.

Đầu vào và đầu ra

Nhóm Đầu vào Đầu ra Điểm hay
PM Task, priority, blocker State file, summary Nhìn được tiến độ ngay
Agent Yêu cầu, code hiện có Diff, notes, file mới Giữ thay đổi nhỏ và có kiểm soát
Tester Feature cần kiểm tra Test report Có bằng chứng pass/fail rõ
Customer Reviewer Giao diện, luồng thao tác UX feedback Phản ánh đúng trải nghiệm thật

Điểm hay

  • Phân tầng rõ nên không lẫn giữa quy ước, trạng thái và phản hồi.
  • Có rule chia nhỏ file để giảm tràn context khi task lớn.
  • Có PM đứng đầu nên luôn có nơi chốt quyết định.
  • Có reviewer từ góc nhìn khách hàng nên không chỉ đúng kỹ thuật mà còn đúng trải nghiệm.

Gợi ý thêm rule và workflow

Rule / Workflow Ý nghĩa
Single Responsibility Mỗi file chỉ làm một việc chính.
Verify Before Merge Kiểm tra xong mới chốt thay đổi.
Intake → Clarify → Plan Chuẩn cho task còn mơ hồ.
Review → Feedback → Action Chuẩn cho vòng phản hồi từ khách hàng.
QA → Fix → Recheck Chuẩn cho bug fix nhiều vòng.
